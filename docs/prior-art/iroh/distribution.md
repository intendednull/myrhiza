## Cadence: roughly monthly, sometimes faster

Iroh's release rhythm has stabilized at one minor version every 3–6 weeks, with patch releases between when needed. Recent cadence verified from the [GitHub releases page](https://github.com/n0-computer/iroh/releases) and [crates.io](https://crates.io/crates/iroh):

Cross-crate compatibility is *not* enforced by version-number alignment — it's enforced by `iroh-blobs` requiring a specific `iroh` minor in its `Cargo.toml`.

## Pre-1.0 versioning policy: every minor is breaking

Iroh follows the standard Cargo pre-1.0 convention: under SemVer, `0.x.y → 0.(x+1).z` is a breaking change, and the iroh team treats it as one. The release notes flag breakages explicitly with `[**breaking**]` markers — see for example the [v1.0.0-rc.0 changelog](https://github.com/n0-computer/iroh/releases/tag/v1.0.0-rc.0), which lists each breaking commit with the `[**breaking**]` tag and a link to the PR. The notes are auto-generated by [`git-cliff`](https://github.com/orhun/git-cliff) (config in [`cliff.toml`](https://github.com/n0-computer/iroh/blob/main/cliff.toml)) so the discipline is mechanical rather than human, which is good — nothing slips.

The breakages are real. Examples from the recent few releases:

- **0.93 → 0.94** — `NodeId` → `EndpointId` rename touches every line that types a peer.
- **0.97 → 0.98** — `Incoming::local_ip` replaced with `Incoming::local_addr`, `ConnectionInfo` replaced with `WeakConnectionHandle`, several enums made non-exhaustive.
- **0.98 → 1.0-rc.0** — `Source` made private; `noq Written` reexport removed; relay auth-token API; QNT config defaults changed.

A user upgrading two minors typically needs an afternoon to chase compile errors. A user upgrading four typically rewrites parts of their endpoint setup.

## Release notes culture: surprisingly good

The auto-generated `git-cliff` changelogs are **structured, complete, and honest**. Every release page lists features, fixes, refactors, docs, and breaking changes by crate, each entry linked to the PR and the commit. No summary blurb on top hiding the diff — the changelog *is* the release note. This is materially better than most pre-1.0 Rust crates, where release notes are either absent, hand-written and sparse, or "see commits."

The trade-off: there is **no narrative migration guide.** When `NodeId` became `EndpointId`, the [release post](https://www.iroh.computer/blog/iroh-0-94-0-the-endpoint-takeover) gave a high-level explanation, but no `0.93 → 0.94` upgrade guide of the kind Holochain publishes. You diff your code against the release notes and figure it out. For a library at this maturity that's defensible; for downstream Myrhiza developers it means we'll be the ones authoring the migration notes for our users.

## Pinned-dep guidance for downstream Cargo.toml

The conservative pattern, given the cadence:

```toml
[dependencies]
iroh = "=0.98.2"             # exact pin — accept no surprises
iroh-blobs = "=0.101.0"
iroh-gossip = "=0.99.0"
```

Rationale: tilde (`~0.98`) and caret (`^0.98`) both *forbid* `0.99` since under Cargo's pre-1.0 rules `0.x → 0.(x+1)` is breaking. So `iroh = "0.98"` already pins to the 0.98 minor. The `=` form additionally pins the patch — useful when you want bug-for-bug reproducibility against a known-tested combination. The downside of `=` is `cargo update` becomes a no-op for that crate; periodic manual bumps are required.

Pin **all** of `iroh`, `iroh-relay`, `iroh-base`, and any data-plane crates (`iroh-blobs`, `iroh-gossip`, `iroh-docs`) together. Mismatches between `iroh-blobs` and `iroh` produce real errors, often delayed-binding ones. Lock-step is the only safe shape.

For 1.0+, once it lands, the standard `^1.0` pattern will give you minor + patch updates automatically — the ABI freeze is the entire point of cutting 1.0. Until then, treat iroh as a churning dependency with auto-generated diff notes, not a stable substrate.

## Mobile / FFI artifact distribution

**[`iroh-ffi`](https://github.com/n0-computer/iroh-ffi)** is unmaintained for production use. The README opens *"This repository is archived and provided as a reference example only,"* but the GitHub `archived` flag is *not* set as of 2026-05-08 (last push 2026-02-07; n0 paused active maintenance in Feb 2025). The repo contains UniFFI-based bindings for Kotlin, Swift, Python, JS — no published artifacts on Maven Central, CocoaPods, PyPI, or npm; users built locally. Last published release was `0.35.0` in June 2025. Treat it as a reference, not a path to production mobile.

The replacement story has two parts:

- **[`iroh-c-ffi`](https://github.com/n0-computer/iroh-c-ffi)** — Active (last push Apr 2026). C ABI for embedding iroh in non-Rust runtimes. The basis on which downstream language wrappers can be built.
- **[`iroh-js`](https://github.com/n0-computer/iroh-js)** — Node.js bindings via `napi-rs`. **Dormant** — last GitHub push 2023-12-07. Despite the name suggesting an active replacement for JS users, the repo has had no real activity for two and a half years; do not rely on it.

The team's current public position (per blog and Discord): production iOS/Android bindings are paid engineering services from Number 0, not freely available artifacts. **There is no shipping iroh on Android or iOS via pre-built binaries from n0 today.** Apps that need iroh on mobile build it themselves from `iroh-c-ffi` or hire n0.

The practical implication: **mobile distribution of any Myrhiza-on-iroh build is our problem.** Cross-compilation, code-signing, app-store review, OS-specific networking quirks (iOS background-mode restrictions on UDP sockets, Android battery-optimization killing long-lived connections) are not solved upstream.

## Implications for Myrhiza

A Myrhiza spec author committing to iroh as a dependency will need to make explicit decisions about how to track its churn. The pre-1.0 cadence and the absence of a wire-format spec (see [`./open-problems.md`](./open-problems.md)) together mean the dependency cannot be treated as a stable substrate — version, wire format, and API surface all move together. The realistic choices:

- **Pinning policy.** Tracking `main` or pulling `git` dependencies is high-risk because the wire protocol shifts under feature branches; `=` pins to crates.io give reproducible builds at the cost of manual bumps. The conservative choice is `=` pins on every iroh-family crate together (mismatches between `iroh-blobs` and `iroh` produce real, often delayed-binding errors).
- **Upgrade cadence.** Lagging the latest stable by one minor is a defensible default — old enough that bugs surface, new enough that breaking-change debt doesn't compound. The `[**breaking**]` markers in the git-cliff changelogs make weekly review of new releases tractable.
- **Vendoring vs forking.** Iroh's surface is large enough that productive forking is unlikely; the realistic exit strategy if iroh becomes intolerable is switching transports, not vendoring. That decision belongs in an architecture spec, not in distribution policy.
- **Mobile distribution.** The current FFI story (see above) means mobile artifact distribution will not come from upstream. The realistic options are: pay n0 for commercial bindings, build our own UniFFI / `napi-rs` layer atop `iroh-c-ffi`, or use Component Model + `jco` for the browser path. Each has different operational costs; the choice depends on which platforms Myrhiza commits to first.

These are decisions to make explicitly in a Myrhiza ops spec, not assertions to inherit from this file.
