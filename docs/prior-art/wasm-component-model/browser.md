# Component Model: Browser Story

## The substrate has no native browser support

As of 2026-05-09 there is no native Component Model implementation in any browser. The WebAssembly JS Interface (the spec at `webassembly.github.io/spec/js-api/`) covers core wasm only: `WebAssembly.Module`, `WebAssembly.Instance`, the JS-side `Memory`/`Table`/`Global` types. Component-typed imports/exports, WIT, the canonical ABI — none of those have a JS-side counterpart in any browser engine today.

The Component Model spec's `design/mvp/Explainer.md` does include a "JavaScript embedding" section sketching what a native browser CM API could look like (a hypothetical `WebAssembly.Component` constructor parallel to `WebAssembly.Module`, plus an ESM-integration story). That sketch is design-stage. No engine has shipped it.

The browser path is therefore *userland transpilation*: take a binary component, run it through a tool that emits regular JS plus regular core wasm, and load that.

## `jco`: the browser transpilation toolchain

`jco` (`github.com/bytecodealliance/jco`) is the Bytecode Alliance's JS-side Component Model toolchain. As of 2026-05-09 the latest npm release is `@bytecodealliance/jco@1.19.0` (published 2026-04-22, verified via the npm registry API). The package's `dist-tags` are `latest: 1.19.0` and `rc: 1.17.9-rc.0`. Releases on the GitHub repo run on a few parallel tracks (`jco-vX.Y.Z` for the CLI, `js-component-bindgen-vX.Y.Z` for the Rust crate that powers transpilation, and `preview2-shim-vX.Y.Z` for the runtime shim); the latest verified release tags are:

- `jco-v1.19.0` (2026-04-22)
- `jco-v1.18.1` (2026-04-20)
- `js-component-bindgen-v1.18.0` (2026-04-29)
- `preview2-shim-v0.17.9` (2026-04-17)

The npm package has 106 published versions, indicating an active release cadence.

### What `jco transpile` does

Given a `.wasm` binary component, `jco transpile foo.wasm -o ./out` produces:

1. **The original core wasm modules**, extracted from the component wrapper and emitted as separate `.wasm` files (or as a single bundled module, depending on flags).
2. **A JS shim per component**, exporting an idiomatic JS API. The shim is a regular ES module that, on instantiation, fetches and instantiates the core wasm modules and supplies their imports via lifted/lowered JS shims.
3. **A TypeScript declaration file** describing the WIT-level types in TS terms.

The shim is what does the canonical-ABI work in JS-land. Lowering a JS object into the core wasm linear memory means:
- Negotiating a `realloc` call into the core module to get a buffer.
- Encoding strings via `TextEncoder` (defaulting to UTF-8).
- Walking record / variant / list structure recursively, writing per the layout rules in [abi.md](abi.md).

Lifting goes the reverse direction: read raw bytes via `DataView`, decode strings via `TextDecoder`, walk the layout backwards into a JS object.

The shim source is generated by `js-component-bindgen` (Rust crate) compiled to a wasm component itself, then transpiled-by-jco-itself and shipped inside the npm package. Bootstrapping is intentional — `jco` eats its own dogfood for the transpiler core.

### `componentize-js`: source → component

The reverse direction (JS source → wasm component, not component → JS) is handled by a separate package, `bytecodealliance/componentize-js`. Latest release is `0.20.0` (2026-04-14), with `0.19.4-rc.1` 2026-03-10 preceding it. componentize-js bundles a SpiderMonkey-derived JS engine into a wasm core module with the user's JS source as data, then wraps the result as a component. The output is a wasm component that *contains* a JS interpreter — a heavy artifact, but one that lets WIT-typed APIs be implemented in JS.

For Myrhiza, componentize-js is relevant only on the *production* side (a JS-authored Myrhiza app being compiled to a component). On the *consumption* side (a Myrhiza component running in the browser), `jco transpile` is the load-bearing tool.

## `preview2-shim`: WASI in the browser

A transpiled component that imports `wasi:io`, `wasi:clocks`, `wasi:filesystem`, etc. needs those imports satisfied in JS-land. `@bytecodealliance/preview2-shim` is the npm package that does this, currently at `preview2-shim-v0.17.9` (2026-04-17). The shim implements each preview2 interface in JS, mapping to:

- **`wasi:io/streams`** → JS streams (`ReadableStream` / `WritableStream`) where appropriate, polyfilled otherwise.
- **`wasi:clocks/monotonic-clock`** → `performance.now()`.
- **`wasi:clocks/wall-clock`** → `Date.now()` / `performance.timeOrigin`.
- **`wasi:random`** → `crypto.getRandomValues()`.
- **`wasi:cli/stdin`/`stdout`/`stderr`** → process streams in Node, console streams in browsers.
- **`wasi:filesystem`** → emulated against an in-memory FS or Node's `fs` module. *Browser context: no real filesystem; preopens are empty by default.*
- **`wasi:sockets`** → **not implemented in the browser**. Browser sandbox prohibits raw TCP/UDP. Node-side, the shim wraps `net.Socket`. A component that imports `wasi:sockets` simply will not run in a browser via `jco`.
- **`wasi:http`** → the browser shim maps to `fetch()`; the Node shim maps to `node:http`.

The shim is per-environment: jco's transpile output references the appropriate shim path at import time, and the bundler resolves to the browser or Node implementation.

### Preview3 / async status in jco

Preview3's native async story is not in stable `jco` as of 2026-05-09. The `preview3-shim` package exists in the jco repo (visible in the README's organization table: "Library that provides a mapping of WASI Preview 3 for NodeJS") but is Node-only and tracks the preview3 release candidates (latest `v0.3.0-rc-2026-03-15`; three RCs total cut 2026-01-06, -02-09, -03-15). Browser-side preview3 support is not shipped. Specs that need to run in browsers today must target preview2.

## Browser limitations vs native Wasmtime

| Capability | Native (Wasmtime) | Browser (`jco transpile` + `preview2-shim`) |
|---|---|---|
| `wasi:io` poll-based streams | yes | yes (mapped to JS streams) |
| `wasi:clocks` monotonic + wall | yes | yes (`performance.now()`, `Date.now()`) |
| `wasi:random` | yes | yes (`crypto.getRandomValues()`) |
| `wasi:filesystem` real FS | yes | no — emulated/in-memory only |
| `wasi:sockets` TCP/UDP | yes | no — browser sandbox forbids |
| `wasi:http` server | yes | no — `fetch()` is client-only |
| `wasi:http` client | yes | yes (`fetch()`) |
| Preview3 native async | yes (Wasmtime tracks preview3) | not in browser; Node-only via `preview3-shim` |
| Threading (`🧵`) | partial / experimental | no |
| Component-level start (`🪙`) | yes | yes |
| Native CM browser API | n/a | not shipped in any engine |

## Other browser-relevant runtimes

- **Fastly Compute** uses jco internally to run components at the edge — same transpilation path, different host bindings (Fastly's own host APIs replace much of `wasi:*`).
- **`wasmtime serve`** and **`wasm-tools`** can target Node via jco's tooling but are not browser-native.

There are no other live browser-side Component Model toolchains as of 2026-05-09. jco is the path.

## Implications for Myrhiza

Myrhiza's design treats browser viability as a first-class deployment target. The substrate's browser story is therefore a real constraint, not an optional bonus.

- **Browser deployment = `jco transpile` of every component.** Each Myrhiza component (kernel-side too, if portions of the kernel ship as wasm) must transpile cleanly. This is a build-time step, not a runtime cost.
- **Kernel host imports must have JS implementations.** Myrhiza's `myrhiza:peer`, `myrhiza:state`, etc. are not WASI interfaces — `preview2-shim` won't help. Myrhiza must ship its own browser-side shim that implements these imports against browser APIs (WebSockets / WebRTC / IndexedDB / SubtleCrypto). This shim is *the browser kernel*. The wasm kernel components and the JS-side kernel implementation have to remain in lockstep.
- **No `wasi:sockets` reliance.** Any Myrhiza interface that conceptually needs a socket has to be designed against `wasi:io/streams` (or its preview3 successor) with the kernel doing the actual transport. The kernel-side network is WebSockets / WebRTC in browser, raw sockets natively. Components see only streams.
- **No `wasi:filesystem` reliance.** Same pattern: storage is a kernel-mediated capability, not a filesystem. A Myrhiza component that wants persistence imports a `myrhiza:storage` (or similar) interface; the kernel-side implementation is real FS natively, IndexedDB-backed in browser.
- **Preview2 baseline.** Spec against preview2's poll-based streams. Preview3's async would be nicer but is browser-non-viable today.
- **Determinism is preserved by the substrate.** A `state-apply` component running in the browser via jco is just as deterministic as one running in Wasmtime — the canonical ABI's lift/lower behavior is fully specified, and jco is a faithful implementation. Kernel-side non-determinism (e.g. clock readings) doesn't leak through because `state-apply` worlds don't import non-deterministic interfaces.
- **Bundle size is real.** A jco-transpiled component is the original core wasm bytes plus a JS shim plus the relevant `preview2-shim` interfaces plus, for JS-authored apps, a SpiderMonkey-sized componentize-js artifact. Myrhiza apps authored in Rust → wasm avoid the SpiderMonkey weight; apps authored in JS pay for it. This matters for first-load performance.

This is the "browser viability" axis the [docs catalog](../../README.md) tracks for the substrate.
