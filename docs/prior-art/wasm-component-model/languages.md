# Component Model — Authoring Languages

This file surveys what each source language can actually produce in the
WASM Component Model, today. The audience is Myrhiza spec authors deciding
which languages we can realistically promise to app developers.

For the tools themselves see [`tooling.md`](./tooling.md). For the spec see
[`spec.md`](./spec.md). For ABI details (which determine how cleanly each
language maps onto WIT types) see [`abi.md`](./abi.md). For preview2 / preview3
streams and futures status see [`preview-status.md`](./preview-status.md).
For honest assessment of cross-language gaps see [`critiques.md`](./critiques.md)
and [`open-problems.md`](./open-problems.md). For lessons we can take into
Myrhiza see [`lessons.md`](./lessons.md). Bundling alternatives appear in
[Agoric's bundle-source story](../agoric-endo/modules-and-bundling.md).

Versions verified 2026-05-09. Treat them as a snapshot — most of these
toolchains are pre-1.0.

---

## Cross-cutting feature matrix

The component model has a moving frontier. Three features matter most for
language support:

- **Resources.** WIT `resource` types — opaque handles with methods. Most
  languages can import resources cleanly; *exporting* resources (i.e.
  letting a language define its own resource type that other components
  use) is harder and varies wildly.
- **Async.** Preview2 has resources and partial async; preview3 (in
  progress) introduces native async functions. Today most languages
  emulate async via callbacks or block.
- **Streams / futures.** WIT `stream<T>` and `future<T>` types — preview3
  feature. Almost no language has full guest-side support yet.

| Language    | Import resource | Export resource | Async (today) | Streams |
|-------------|-----------------|-----------------|---------------|---------|
| Rust        | yes             | yes             | partial (callback) | partial |
| TinyGo      | yes             | partial         | no            | no      |
| JavaScript  | yes             | yes             | yes (native Promise) | partial |
| Python      | yes             | yes             | partial       | no      |
| C/C++       | yes             | manual          | no            | no      |
| Java (TeaVM)| yes             | partial         | no            | no      |
| MoonBit     | yes             | yes             | partial       | no      |
| Zig         | partial         | manual          | no            | no      |
| Swift       | none            | none            | none          | none    |

"Manual" means the language can do it but the bindgen does not produce
ergonomic wrappers — you write the canonical-ABI dance by hand.

This table is best-effort as of 2026-05-09; verify against the latest
`wit-bindgen` and language-specific tooling before relying on a cell.

## Rust — the reference path

**Toolchain.** `wit-bindgen` 0.57.1 (macro and CLI), `cargo-component`
0.21.1, `wasm-tools` 1.248.0 for finishing. Rust nightly's `wasm32-wasip2`
target is the migration destination; `wasm32-wasip1` plus `wasm-tools
component new` is the still-common path.

**Authoring shape.** A Rust component is a Rust crate with `crate-type =
["cdylib"]` whose `lib.rs` contains:

```rust
wit_bindgen::generate!({ world: "my-world", path: "wit" });

struct Component;

impl Guest for Component {
    fn run(input: String) -> String { /* ... */ }
}

export!(Component);
```

**Resources.** Both import and export work via the macro. Imported
resources show up as Rust types with methods; exported resources require
implementing a trait (`GuestResource`) and the bindgen wires the canonical-
ABI handle traffic.

**Async.** The currently-shipping path is sync — `Guest` trait methods are
plain `fn`. Preview2 host imports that look async (e.g. WASI HTTP) are
exposed via callback-style polling. Native `async fn` in WIT is preview3
and not yet stable; some experimental `async-trait`-style work exists in
`wit-bindgen`.

**Gotchas.** Compile time is real (the macro re-runs on every WIT touch).
The interaction between the macro and rust-analyzer is mediocre. Default
ABI is canonical CABI; opting into preview2 streams is gated.

**For Myrhiza.** Rust is our reference authoring path for app authors. The
ergonomics are best-of-breed and the Rust generator gets the most attention
upstream. State-apply components in particular benefit from Rust's
deterministic `no_std` story — easier to enforce "no clocks, no RNG" than
in any other listed language.

## Go (TinyGo) — usable, not full Go

**Toolchain.** TinyGo 0.41.1 (2026-04-22) on Go 1.23+. Build target:
`tinygo build -target=wasip2 -o app.wasm app.go` (the modern target name;
the older `wasi-component` flag is deprecated). WIT bindings generated by
the in-tree `tinygo` `wit-bindgen` integration.

**Status.** Functional. TinyGo has had component-model support since 0.33
or so and the integration has tightened with each release. Resources work
in the import direction; export-side resource support is partial — the
generator emits the trait but corner cases (resource methods returning
resources of the same type, finalisers) still bite.

**Limitations.**

- **TinyGo is not full Go.** Reflection is partial, the `unsafe` package is
  partial, `cgo` does not work, and several stdlib packages are stubbed.
  Most network code (`net`) only works through WASI imports, not directly.
  Goroutines work but with TinyGo's scheduler, not Go's.
- **GC.** TinyGo uses a conservative mark-sweep GC at wasm. Pause times
  are typically fine but not engineered for low-latency.
- **No native async.** Component-model async functions are not yet
  generated for Go.

**For Myrhiza.** Acceptable as a "yes, you can write Myrhiza apps in Go"
answer, with caveats. Go-developer mental models (goroutines, full stdlib,
`net.Dial`) do not transfer. Authors should expect to write
component-shaped Go, not idiomatic Go.

## JavaScript — best ergonomics, biggest binary

**Toolchain.** `componentize-js` 0.20.0, `jco` 1.19.0. Both are npm
packages. The bundled engine is StarlingMonkey (SpiderMonkey-based,
embedded variant from Fastly / Bytecode Alliance).

**Authoring shape.** Write idiomatic ES modules. The exported functions
of the module map to the WIT world's exports.

```js
// app.js
export function run(input) { return input.toUpperCase(); }
```

```
jco componentize app.js --wit ./wit --world-name my-world --out app.wasm
```

**Resources.** Imported resources show up as JS classes; exported
resources are also JS classes that the toolchain wires into canonical-ABI
handle traffic. The mapping is reasonably idiomatic.

**Async.** JS is the *one* language where async maps cleanly today — WIT
async functions show up as `async function` returning Promises, and
`componentize-js` handles the event-loop integration. This is the leading
edge of guest-side async.

**Streams / futures.** Partial. Streams of bytes (HTTP body etc.) work via
async iterables; arbitrary `stream<T>` is incomplete.

**Tradeoffs.**

- **Size.** Minimal "hello world" component is roughly 5–10 MB because the
  JS engine is bundled. Bytecode Alliance has invested in WIZER pre-init
  and code-cache snapshotting; cold-start is fast even though the binary
  is large.
- **Performance.** JS-engine speed, with no JIT (the bundled engine is
  interpreted in component-model mode for sandboxing reasons). Fine for
  glue, slow for hot loops.

**For Myrhiza.** A reasonable "second-tier" language for app authors. The
async ergonomics are unmatched. The size cost is the issue — if Myrhiza
peers run on resource-constrained hardware the per-app overhead adds up.

## Python — same shape, similar tradeoffs

**Toolchain.** `componentize-py` 0.23.0 (2026-04-15). Bundles CPython.

**Authoring shape.**

```python
class Component:
    def run(self, input: str) -> str: return input.upper()
```

```
componentize-py -d wit -w my-world componentize app -o app.wasm
```

**Resources.** Imported and exported resources both work; the generator
emits Python classes, methods, and `__del__` finalisers wired to the
canonical-ABI drop semantics.

**Async.** `componentize-py` has experimental support for `async def`
exports mapping to WIT async functions, but it's behind preview3 features
and version-fragile. The sync path is the recommended one.

**Streams / futures.** Not yet.

**Tradeoffs.** Same shape as JS — bundled CPython adds tens of MB,
steady-state performance is CPython, cold-start is fast post-WIZER. Python
feels slightly worse than JS for component authoring because Python's
async story is itself less coherent than JS's.

**For Myrhiza.** Same answer as JS: accept it as a producer, don't
recommend it as a default.

## C / C++ — the assembly-language path

**Toolchain.** `wit-bindgen c` (in-tree) generates C headers and source
implementing the canonical ABI for an imported WIT world. On the guest
side, the WASI SDK ships clang + libc + relevant adapter modules. The
typical flow:

```
wit-bindgen c ./wit --world my-world --out-dir bindings
clang --target=wasm32-wasip2 \
      bindings/my_world.c app.c \
      -o app.wasm
wasm-tools component new app.wasm -o component.wasm
```

**Resources.** Imports work via opaque handle types and accessor
functions. Exports require manually implementing the destructor / method
dispatch — workable but tedious.

**Async.** None. C has no native async; the bindgen does not synthesise
event-loop scaffolding.

**Streams / futures.** Not exposed.

**For Myrhiza.** Useful as an escape hatch — anyone with existing C/C++
code can produce a component. Not a recommended app-authoring path. The
canonical-ABI dance shows through, and writing a deterministic
`state-apply` in C is asking for the kind of UB that breaks cross-peer
convergence.

## Java (TeaVM) — niche but exists

**Toolchain.** TeaVM (a Java-bytecode-to-wasm compiler) has component-
model support via its own `wit-bindgen`-style generator. Maturity is
behind Rust / JS / Go. Not all Java stdlib classes survive the TeaVM
translation.

**Status.** Works for modest Java code. Resource export support is
partial. Async is not native. Effective Java-on-wasm is a small community
compared to TinyGo or Rust.

**For Myrhiza.** Tertiary at best. We wouldn't promise it but wouldn't
reject components produced this way.

---

## MoonBit — first-class CM, small footprint

**Toolchain.** MoonBit is a relatively new language (Moonbit / IDEA team)
that targets WASM and has had component-model support in `wit-bindgen` since
0.40-something — `wit-bindgen moonbit` is in-tree as of 0.57. Output binaries
are small (no bundled runtime — MoonBit compiles to wasm directly with a
small runtime).

**Status.** Improving fast; relevant for "small idiomatic component in a
language other than Rust". Toolchain ergonomics are mediocre but
component-model fidelity is reasonable.

**For Myrhiza.** Watch-item. Probably not a primary target but worth
revisiting in 6–12 months.

---

## Zig — partial support, mostly DIY

**Toolchain.** Zig compiles to wasm easily (`zig build-lib -target
wasm32-wasi`). No first-class component-model bindgen — there are
community generators (`zig-witx`, hand-rolled) but nothing in-tree in
`wit-bindgen`. Practical authoring path is "produce a core wasm module,
embed WIT manually with `wasm-tools component embed`, run `wasm-tools
component new`".

**Status.** Doable, hand-rolled. Resources require writing canonical-ABI
glue manually.

**For Myrhiza.** Escape hatch only. Zig users who want components today
write the C-style bindings.

---

## Swift — none yet

**Toolchain.** SwiftWasm exists and produces wasm core modules from Swift
code. There is no first-class component-model toolchain — no `wit-bindgen
swift`, no `componentize-swift`. Discussion has happened on the SwiftWasm
side but no shipped artifact. Verify before assuming anything has changed.

**For Myrhiza.** Not viable today. Swift app authors would need to write
core wasm and stitch components manually — effectively the C path with more
ceremony.

## Cross-cutting: how the resource and async stories matter for Myrhiza

Myrhiza apps will use resources for any handle the kernel hands out
(state-store handles, network sockets, signed-event constructors, etc.)
and async wherever I/O is not synchronous. The language matrix above
collapses to a few practical questions:

- **Can the language *export* a resource?** Matters if a Myrhiza app wants
  to define its own resource that *other* components use (e.g. an app
  exposing a query handle to its own UI component). Today: Rust and JS
  cleanly, Python adequately, others partial. If we don't need cross-
  component resources within an app bundle, this is moot.
- **Can the language *consume* an async host import?** Matters because the
  kernel will expose async I/O. Today: JS cleanly, Rust via callbacks,
  others mostly sync. Sync clients of async hosts effectively block — fine
  for state-apply (which has no I/O), bad for `behavior` components doing
  network work.
- **Determinism enforceability.** state-apply components must be pure.
  Rust gives us the strongest tools to enforce this (no_std, careful crate
  selection, compile-time checks). JS / Python are *much* harder to make
  deterministic — the engines themselves do non-deterministic things
  (allocator, GC, time of last GC). For state-apply we likely require
  Rust; for `propose`, `interaction`, `behavior` we can be permissive.

## What Myrhiza realistically promises

A defensible authoring-language stance for Myrhiza:

- **Rust — first-class.** Best ergonomics, best determinism story, best
  cross-feature support. Recommended for all four component profiles, and
  *required* for `state-apply`.
- **JavaScript — supported.** Acceptable for `interaction` and `behavior`
  profiles where the size / determinism tradeoffs are tolerable.
- **Python — accepted.** Same answer as JS, lower priority.
- **Go (TinyGo) — accepted.** Lower priority again. The "this is not real
  Go" footgun is real; doc it heavily.
- **C / C++ — escape hatch.** Anyone with existing native code can produce
  a component. We don't recommend it but we run the result.
- **Everything else — runs if it produces a valid component.** No
  guarantees on ergonomics, examples, or support.

The single load-bearing decision is Rust as `state-apply` author. Every
other language slot is negotiable.
