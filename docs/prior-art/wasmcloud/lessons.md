# Lessons for Myrhiza

This is the consult-this-when-designing file. The other wasmCloud prior-art files are evidence; this file is decisions.

wasmCloud is the **closest existing art** to a production CM runtime that brokers I/O via capabilities. Treat it as a near-peer architecture: every cell in these tables has to earn its place, because we're choosing what to copy verbatim, what to learn from in the negative, and what to actively rework.

The framing: **validates** is what wasmCloud's seven years of production usage confirm about Myrhiza's design instincts. **Avoid** is what wasmCloud chose that Myrhiza must not. **Borrow** is concrete techniques to import — direct precedent for specs we'll write.

## Validates

Myrhiza design choices that wasmCloud's experience confirms.

| Pattern | What wasmCloud does | Why it validates Myrhiza | Myrhiza application |
|---|---|---|---|
| **Components import-only; providers implement.** | wasmCloud components have no native I/O. Every host-side capability (HTTP, KV, blobstore, secrets) is a separate component (v2) or provider (v1) that the lattice/host satisfies via WIT-typed link. | Direct production validation of "the runtime owns I/O; components are pure compute over WIT-typed imports." Seven-year track record across thousands of deployments. | Direct precedent for kernel-mediated host imports. The kernel *is* the wasmCloud host; capabilities are the kernel's WIT exports. See spec for kernel ABI. |
| **Interface-typed addressing, not name-based.** | A component imports `wasi:keyvalue/store.get(k)`; the lattice routes to whichever provider implements `wasi:keyvalue/store` with the right link config. The component doesn't know which provider, where, or how. | Validates "component A can call any peer that exports interface X" without A knowing peer identity. The interface is the address. | Adopt as the routing primitive for cross-peer capability calls. Map WIT-interface to (peer set, capability handle); kernel routes. |
| **Link definitions as runtime-mutable.** | wadm reconciles toward declarative spec; wasmCloud reconfigures live links without restarting components. | Capability revocation is a *live re-binding*, not a redeploy. Production runtime confirms the operational primitive works. | Myrhiza capability revocation = drop the capability handle; next host import resolves with new authority state. Direct copy of the operational shape. |
| **Component Model + WIT as the only ABI.** | Post-v1.0 wasmCloud is CM-only; the actor ABI is gone. wRPC speaks WIT-types over the wire. | The actor → component rewrite cost wasmCloud significant developer-years. Their conclusion (CM is the only ABI worth having) is dearly bought. | Don't ship a non-CM ABI. Don't ship a "lite" ABI for small components. CM is the floor. |
| **Capability provider as a separate component / process.** | wasmCloud v1 capability providers run out-of-process; v2 in-process plugins are loaded into the host. Either way, they're a *named, versioned, replaceable* unit. | Validates "the I/O surface is a swappable component, not a built-in." Operators can replace `wasi:keyvalue/store` impl at runtime. | Myrhiza's host-imports are kernel-implemented but the *implementation* is a swappable strategy: in-kernel stub, separate component, native fallback. Same shape; different defaults. |
| **OCI-as-component-registry.** | wasmCloud was an early adopter of OCI for shipping components; the [wasmcloud-oci-distribution](https://github.com/wasmCloud/oci-distribution) work is upstream-influential. Components ship as OCI artifacts with the WASM blob + claims metadata. | Validates "use OCI; don't invent a new artifact format." Tooling, registries, mirrors, signing — all already exist. | Adopt OCI as Myrhiza's app-bundle distribution format. iroh-blobs for content-addressed P2P transport, OCI as the schema for what's inside. See spec for app-bundle format. |
| **Declarative reconciliation (manifests → reality).** | wadm: write a manifest declaring components/links/configuration; controller reconciles current state toward declared state. K8s-CRD-shaped. v2 makes this literal: K8s CRDs. | Validates "the desired-state declaration is the operator surface, not imperative commands." Reconciliation tolerates partial failure, restarts, network partitions. | Myrhiza app installs declare *what* the app is; kernel reconciles toward that state across restarts. Don't expose imperative `start_component`; expose declarative `app.toml`-equivalent. |
| **Lattice / addressable component pool.** | wasmCloud horizontally scales by spinning up multiple instances of the same component; calls are load-balanced across the pool by the lattice. | Validates "addressable by interface, not by instance" as a horizontal-scale primitive. | When Myrhiza needs intra-peer parallelism (e.g., a behavior component running on multiple cores), use the same primitive: pool of instances under one interface address. |
| **Signed metadata travels with the bundle.** | wasmCloud "claims" are JWS-signed component metadata: issuer, capabilities granted, version. Embedded in the OCI artifact; verified before instantiation. | Production validation that "the publisher's signature is part of the artifact, not a sidecar." Tooling, registries, and runtimes all carry it transparently. | Adopt the JWS-over-bundle-metadata pattern for Myrhiza app bundles. Publisher signs; kernel verifies before instantiation. |
| **One host = one process, with embedded runtime.** | wasmCloud's host is a single Rust process embedding Wasmtime + the control-plane client + provider runtime. Not a microservice constellation. | Validates "the kernel is one binary, not a swarm." Operationally simpler; debuggability higher; resource accounting straightforward. | Myrhiza kernel is one binary per peer. Don't fragment into kernel-network, kernel-scheduler, kernel-state microservices; embed. |
| **Component lifecycle is kernel-driven, not component-driven.** | Components don't `main()`; the host instantiates them on demand and tears them down. They cannot self-spawn, self-restart, or persist beyond the host's decision. | Validates "the runtime owns lifetime; the component is data + functions." Removes a class of bug where a component can refuse to die. | Components are inert until invoked; the kernel decides instantiation, instance count, and destruction. No component self-control over lifecycle. |

## Avoid

Patterns wasmCloud uses that Myrhiza explicitly does not.

| Anti-pattern | What wasmCloud does | Why Myrhiza should avoid | Myrhiza alternative |
|---|---|---|---|
| **Central NATS for lattice gossip (v1).** | NATS cluster is required; lattice gossip and wRPC both ride on NATS subjects. Federated message broker, hub-and-spoke. | Single point of coordination. Operator owns the broker. NATS partitions = lattice partitions. Anti-thetical to peer-symmetric P2P. | Iroh + gossipsub for symmetric P2P. Each peer is a relay; no privileged broker. See [`../iroh/lessons.md`](../iroh/lessons.md). |
| **K8s API server as scheduling backend (v2).** | wasmCloud v2 dropped the standalone host model; K8s API is now the lightweight scheduler. ([Issue #5020](https://github.com/wasmCloud/wasmCloud/issues/5020).) | Even more centralized than NATS. Requires K8s expertise. Excludes user-device deployment. | No central scheduler. The kernel runs on user devices and decides locally what to run. Distributed scheduling is the app's problem (behavior profile), not the runtime's. |
| **Operator-declared link definitions as authority.** | "Component A may call interface X" is decided by a human operator writing wadm config. Authority is RBAC, not capability. | This is not capability-discipline. The component holds no unforgeable authority; the broker decides per-call. Doesn't compose; doesn't delegate; doesn't revoke cleanly. | Myrhiza grants capabilities cryptographically (signed grant, holder-bearer, transferable). Closer to OCapN. See [`../spritely-ocapn/lessons.md`](../spritely-ocapn/lessons.md). |
| **Live-only execution; no replay.** | wasmCloud has no event log, no deterministic replay, no consensus. Components run; results are lost on host crash. | Myrhiza's `state-apply` profile *requires* deterministic replay for cross-peer convergence. Borrowing wasmCloud's "live-only" stance breaks state-apply. | State-apply is a deterministic function over an event log. Wrap it in the kernel's deterministic call envelope. See Agoric SwingSet for the model — [`../agoric-endo/lessons.md`](../agoric-endo/lessons.md). |
| **Lattice-ID multi-tenancy.** | Tenants are NATS subject prefixes; isolation is operator-config + NATS-account-config. Get the config wrong, tenants leak. | Operator-dependent isolation is a security cliff. We can't accept "if the operator forgot to configure cross-account deny, you have a vulnerability" for user-device deployment. | Capability-discipline as the isolation primitive. Apps cannot name each other's components or capabilities. Cross-app interaction requires explicit cap exchange. |
| **Tooling as parallel CLIs (`wash`, `wadm`, `cosmo`, `washboard`).** | Multiple maintained tools, each with its own version train, install path, config file. | Onboarding cost; "which command do I run?" friction. Documented at length in wasmCloud forums. | Single Myrhiza CLI as the canonical operator surface. Don't fragment by concern (cli vs deploy vs ui); fragment by audience (developer vs operator) only if needed. |
| **Heavy host process (Wasmtime + control plane + NATS client + provider runtime).** | Hard floor on RAM/CPU per host. Issue [#4940](https://github.com/wasmCloud/wasmCloud/issues/4940) acknowledges per-instance datafusion components consume large RAM at scale. | Myrhiza runs on user devices. A 500MB-RAM idle process is unacceptable; even a 50MB one is questionable. | Engineer the kernel for sub-50MB idle. Component instance deduplication is a v0 feature, not a v2 wishlist. |
| **Server-only deployment.** | No browser-host runtime. Browser path was an RFC that closed without shipping. | Myrhiza must run in the browser as a peer. Interaction-profile components render UI client-side. | Two kernel flavors from day one: native (Wasmtime) and browser (jco). See [`../wasm-component-model/browser.md`](../wasm-component-model/browser.md). |
| **Single-implementation; spec lags code.** | One Rust host. WIT packages versioned ad-hoc. wRPC has no published wire spec separate from the implementation. | Cross-peer interop in Myrhiza must work without all peers running our binary. | Specs-first for everything that crosses a peer boundary: kernel↔kernel gossip, capability handshake, app-bundle wire format. Implementation conforms to spec, not vice versa. |
| **Vendor-led roadmap (Cosmonic).** | wasmCloud's v2 K8s pivot followed Cosmonic's commercial focus. CNCF backstop didn't prevent the architectural realignment. | Borrowing wasmCloud patterns means borrowing wasmCloud's *future direction* by inertia. We have to filter for technique, not strategic posture. | Treat wasmCloud as a snapshot of working techniques, not as a project we track. Pin our learnings against v1 architecture; ignore v2 pivot for design purposes. |
| **Live-only execution; lost component state on host crash.** | wasmCloud has no checkpointing; a host crash loses every in-flight invocation and every component instance's RAM. Recovery is "restart from declared state." | Acceptable for stateless function-style components on datacenter hardware. Unacceptable for long-lived peer streams on user devices that flap network constantly. | Components are stateless by construction; durable state lives in kernel-managed stores (event log + materialized projections). Recovery = re-instantiate, replay, resume. |
| **Spec-as-implementation.** | The wasmCloud Rust host is the spec; WIT packages, wRPC wire format, and lattice protocols have no spec independent of the code. | Acceptable for single-vendor production deployments. Fatal for multi-implementation peer interop. | Specs-first for all wire-format and ABI work. Implementation conforms to spec; spec lives in `docs/specs/`. (Restated from the table above for emphasis: this is the most common spec-vs-code temptation.) |

## Borrow

Concrete techniques to import — direct precedent for specs Myrhiza will write.

1. **Interface-typed addressing as the routing primitive.** wasmCloud's "call `wasi:keyvalue/store.get(k)`, route to whichever provider impls it on the lattice" is the right shape for cross-peer capability calls. Myrhiza adapts: route over Iroh streams + ALPN to the peer-set holding the relevant capability handle. The interface is the address; the cap-handle is the authority. **Maps to:** `docs/specs/<date>-capability-routing-design.md` (TBD).

2. **wadm declarative-manifest model.** k8s-CRD-shaped: manifest declares components, links, configuration; controller reconciles. The shape is right even if the v2 K8s implementation isn't. Myrhiza needs an analogous "app spec" format the kernel reconciles toward. **Maps to:** `docs/specs/<date>-app-manifest-design.md` (TBD).

3. **Capability provider as a host-side WIT-typed endpoint.** A `wasi:keyvalue/store` provider is a WIT-typed component that exports the interface; consumers don't know if it's in-process, out-of-process, or remote. The *shape* is right; Myrhiza's kernel is the "host" that satisfies the import, but it can dispatch to in-kernel code, separate process, or remote peer transparently. **Maps to:** `docs/specs/<date>-host-import-dispatch-design.md` (TBD).

4. **Live re-link semantics.** wasmCloud reconfigures a component's bindings without redeploy. Myrhiza needs the same for capability revocation: drop the capability handle; next host-import call sees the new authority state. The *operational primitive* is right; the v1 implementation (NATS subject re-routing) we don't copy, but the user-visible behavior we do. **Maps to:** `docs/specs/<date>-capability-revocation-design.md` (TBD).

5. **OCI-as-component-registry.** wasmCloud was an early adopter; the schema for component metadata in OCI annotations (claims, signatures, link refs) is upstream-influential. Adopt the OCI shape for Myrhiza's app-bundle format; ship over iroh-blobs for P2P content addressing. **Maps to:** `docs/specs/<date>-app-bundle-format-design.md` (TBD).

6. **wRPC interface-typed wire format.** wRPC encodes WIT calls in a typed wire format; calls are interface-versioned. The *concept* (typed wire format derived from WIT) is right; the *transport* (NATS) we don't use. Adopt typed-wire-from-WIT for kernel↔kernel calls in Myrhiza, riding on Iroh streams instead of NATS subjects. **Maps to:** `docs/specs/<date>-cross-peer-rpc-design.md` (TBD).

7. **Per-WIT-method resource semantics.** wasmCloud's open issue [#4953 \[BUG\] wasmtime host resource types are string comparisons](https://github.com/wasmCloud/wasmCloud/issues/4953) is a precedent for "WIT resource types must be carried by-type, not by-name". Myrhiza's kernel must thread typed resource handles end-to-end without string comparison fallbacks. **Maps to:** kernel ABI spec, resource-type section.

8. **Component pool / horizontal scaling primitive.** wasmCloud's "N instances behind one interface address" is a clean shape. Myrhiza adapts for intra-peer parallelism: the kernel may instantiate multiple copies of a behavior component to use multiple cores; calls round-robin across the pool. **Maps to:** kernel scheduling spec (TBD).

9. **The "claims" / signed-metadata pattern.** wasmCloud components carry signed claims (issuer, capabilities granted, version). The shape is essentially a JWS over component metadata. Myrhiza adapts: app-bundle metadata is signed by the publisher; the kernel verifies before instantiation. **Maps to:** `docs/specs/<date>-app-publishing-design.md` (TBD).

10. **The "host inventory" introspection API.** wasmCloud lets operators query "which components are running where, with which links?" The introspection API is part of the operator surface, WIT-typed, capability-mediated. Myrhiza needs the analogous "what's running on this peer right now?" introspection — useful for debugging, for the user's "running apps" view, and for the kernel's own scheduling. **Maps to:** kernel introspection spec (TBD).

11. **The provider/component split as a process boundary that *can move*.** wasmCloud's v1 → v2 transition relocated capability providers from out-of-process (NATS-fronted) to in-process (host-loaded plugins) without changing the WIT interface they exposed. Components saw the same `wasi:keyvalue/store`; only the dispatch path changed. This is the right architectural posture: **the WIT interface is the contract; the location of the implementation is a kernel decision**. Myrhiza adopts this directly — host imports may be served in-kernel, by a colocated component, or by a remote peer, and the consuming component cannot tell. **Maps to:** kernel ABI spec, dispatch section.

12. **Configuration-as-link-input.** wasmCloud's link definitions carry per-link configuration: "component A links to provider P with config `{prefix: 'orders/'}`." The configuration is the link attribute, not a component-internal value. This makes the same component reusable in different deployments without rebuild. Myrhiza should expose the same shape: capability grants carry per-grant configuration; the same component can be granted multiple distinct configurations of the same capability. **Maps to:** capability-grant spec (TBD).

## Implications for Myrhiza

If you're writing a Myrhiza spec, these are the wasmCloud-derived takeaways most likely to matter:

- **Capability-discipline beats RBAC.** wasmCloud's link-definition model is the wrong authority shape for Myrhiza. Use cryptographic ocaps; let wasmCloud teach us the *operational mechanics* of "capability is a swappable, runtime-mutable handle" without inheriting the RBAC semantics. (See [`../spritely-ocapn/lessons.md`](../spritely-ocapn/lessons.md) for the right authority model.)
- **Interface as address is the routing primitive.** This is wasmCloud's central insight; copy it directly.
- **Determinism is *our* problem, not wasmCloud's.** State-apply runs in a kernel-imposed deterministic envelope. wasmCloud has no model for this; look at Agoric SwingSet instead.
- **No central broker.** Iroh + gossipsub replaces NATS. Every wasmCloud-borrowed pattern (lattice gossip, link reconfig, multi-instance routing) re-implements over a peer-symmetric substrate.
- **Browser is not optional.** wasmCloud is server-only; Myrhiza is not. Plan two kernel flavors from the start.
- **Spec-first interop.** wasmCloud's single-implementation works for them; it fails for us. Wire formats and ABIs all need writable specs other implementations could conform to.
