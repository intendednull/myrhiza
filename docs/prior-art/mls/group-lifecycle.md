This file walks the per-message and per-epoch mechanics. For the cryptographic substrate (HPKE, TreeKEM, ciphersuites), see [`crypto.md`](./crypto.md).

## 1. KeyPackage

A `KeyPackage` is a pre-published bundle a client uploads to the Delivery Service so that *others* can add it to a group while it is offline. This is the asynchronous-add primitive.

Contents (RFC 9420 §10):

- **`init_key`** — an HPKE public key used once, to encrypt the path secret to this member during the Welcome that adds them.
- **`leaf_node`** — the leaf the member will occupy when added. Itself contains:
  - `encryption_key` — HPKE public key for ongoing tree operations.
  - `signature_key` — public signing key for the member.
  - `credential` — the member's identity, validated by the AS.
  - `capabilities` — supported protocol versions, ciphersuites, credential types, proposal types, extension types.
  - `leaf_node_source` — how the leaf was added (`key_package`, `update`, `commit`).
  - `lifetime` (when source is `key_package`) — `not_before` / `not_after`, seconds since Unix epoch. Applications must enforce a max total lifetime.
  - `extensions`, `signature`.
- **`signature`** over the KeyPackage tying the package to the leaf node's signing key.

A KeyPackage is **single-use**: once consumed by an Add, it must not be reused. The DS is expected to invalidate consumed packages. Rotation cadence is application policy — typical practice is to keep a small pool (5–50) per device, refreshed on a timer or on consumption.

## 2. Group creation (epoch 0)

Alice creates the group as the sole member:

1. Alice picks a `group_id` and ciphersuite.
2. She constructs a ratchet tree of size 1: a single leaf with her own `LeafNode`.
3. She runs the key schedule with an init secret of zeros (or a `psk`-derived seed if the group is being branched/reinit'd).
4. The result: epoch 0, group state derived from her leaf alone.

No handshake message is broadcast — there's no one to broadcast to. The state exists locally until she adds someone.

## 3. Add (introducing a new member)

Bob has previously published a KeyPackage. Alice (a current member) wants to add him.

1. Alice fetches Bob's `KeyPackage` from the DS.
2. She constructs an **`Add` proposal** referencing his KeyPackage by hash.
3. She constructs a **Commit** that includes that proposal (inline or by-reference). The Commit:
   - Inserts Bob's leaf in the tree (right-most empty leaf, or extending the tree).
   - Generates fresh path secrets along Alice's direct path to the new root.
   - Encrypts those path secrets to the appropriate sub-trees with HPKE.
   - Advances epoch to 1.
4. Alice produces a **Welcome** message addressed to Bob's `init_key` (from the consumed KeyPackage). The Welcome contains the encrypted group secrets Bob needs to reconstruct the post-commit state.
5. Alice broadcasts the Commit (to existing members) and sends the Welcome to Bob (typically via the same DS).

Bob receives the Welcome, decrypts with the init private key, reconstructs the ratchet tree at epoch 1, and is now a full member.

The Add → Commit pattern is uniform: every change is a `Proposal` referenced by a `Commit`. **Multiple proposals can be batched into one Commit** (e.g. add three members and remove one in a single epoch advance).

## 4. Update (rotating a member's leaf key)

Members rotate their leaf periodically to provide PCS. An Update is the mechanism.

1. Member generates a fresh leaf key.
2. Sends an **`Update` proposal** containing a new `LeafNode` with `leaf_node_source = update`.
3. *Some member* (often a different one — see the "Update is committed by another" pattern in RFC 9420) issues a **Commit** that applies the Update.
4. The Commit re-derives path secrets along the updater's direct path; epoch advances; new keys are derived.

**A member can also Update themselves and Commit in one step** by sending a Commit with a fresh path (no separate Update proposal needed). This is the common case for "I'm acting; while I'm acting let me rotate."

## 5. Remove

1. Some member sends a **`Remove` proposal** identifying the target leaf index.
2. A Commit applies it. The target's leaf is blanked. Path secrets along the removed direct path are regenerated by the committer; the removed member can no longer derive them.
3. Epoch advances. The removed member's old keys decrypt nothing in the new epoch — this is **PCS-with-respect-to-the-removed-member**.

The protocol does not specify *who is allowed* to remove whom — that is application policy enforced above MLS (e.g. "only admins can Remove").

## 6. Commit — the atomic primitive

A Commit is the only message that advances the epoch. It:

1. References a list of pending proposals (by-value or by-hash; by-hash refers to proposals broadcast earlier in the epoch).
2. Optionally includes an `UpdatePath` — the committer's fresh leaf + path secrets up to the new root, HPKE-encrypted to each sub-tree's resolution.
3. Is signed by the committer.
4. Carries a `confirmation_tag` — a MAC over the new epoch's `confirmed_transcript_hash` proving the committer derived the same group state every other member will derive.

Receivers process the Commit by applying the proposals in spec-defined order, decrypting their slice of the new path, deriving the new commit secret, running the key schedule, and verifying the confirmation tag. Any disagreement aborts.

This is where MLS's determinism property lives: every member, given the same Commit, derives bit-identical new group state.

## 7. Welcome

The Welcome message lets a newly-added member skip the entire prior handshake history. It contains:

- `cipher_suite`.
- `secrets` — for each new joiner, their `EncryptedGroupSecrets` (HPKE-encrypted to their KeyPackage `init_key`), containing the joiner secret + path secret + PSKs.
- `encrypted_group_info` — the public group state (`GroupInfo`: ratchet tree, group context, extensions, confirmation_tag, signer), encrypted under a key derived from the joiner secret.

The new member learns *current* state and *no past keys*. They cannot decrypt anything sent before they joined — this is the FS guarantee with respect to new members.

## 8. External commits

For "open" groups (joinable without invitation), MLS supports **external commits** (RFC 9420 §11.2.1).

1. A current member publishes a `GroupInfo` object containing the ratchet tree, group context, and an `external_pub` HPKE key.
2. The new joiner Z fetches the GroupInfo and constructs a Commit of a special form — an `ExternalInit` proposal seeded by an HPKE encapsulation to `external_pub`.
3. Z's Commit adds themselves and broadcasts. Existing members process it like any other Commit.

Key distinction from Add+Welcome: **no Welcome is generated**. Z doesn't need an existing member to act on their behalf; they self-add using the public GroupInfo. Useful for permissionless joins.

## 9. ReInit

`ReInit` (RFC 9420 §11.2) closes one group and starts a new one with the same members and (typically) different parameters — the standard mechanism is **ciphersuite migration**.

1. A `ReInit` proposal names new ciphersuite, version, group_id, extensions.
2. A Commit applies it; the old group is **terminated** at that epoch.
3. A new group is bootstrapped at epoch 0 with the same membership; the joiner secret of the new group includes a **resumption PSK** derived from the old group's final epoch, tying the two groups cryptographically.

This is the path forward for moving an existing group from a classical ciphersuite to a hybrid PQ ciphersuite (see [`crypto.md`](./crypto.md) §7–8).

`Branch` (in `draft-ietf-mls-extensions`) is similar but produces a new group while *keeping* the old one — for forking a sub-conversation.

## 10. Application secret + epoch secret

Each Commit produces a fresh `epoch_secret`, fed by:

- The new `commit_secret` (root secret of the updated ratchet tree).
- The previous epoch's `init_secret`.
- Any optional PSKs.

From `epoch_secret` the key schedule (HKDF-Expand-Label) derives:

- `application_secret` — exported up to the application; per-sender ratchets are seeded from here. Each sender holds an AEAD ratchet: per-message keys derived forward, never backward.
- `init_secret` — input to the *next* epoch's schedule.
- `confirmation_key`, `membership_key`, `resumption_psk`, `epoch_authenticator`, etc.

Per-message AEAD keys are derived once-forward from the sender ratchet and discarded — that's the per-message FS layer below the per-epoch FS.

## 11. Forward secrecy + post-compromise security

**Forward secrecy** comes from two layers:

- *Per-message*: sender ratchet is one-way; capturing key `n` cannot reconstruct key `n−1`.
- *Per-epoch*: each Commit derives a new epoch secret from a fresh `commit_secret`. Past epoch secrets are deleted; an adversary who later compromises `epoch_secret_k` cannot re-derive `epoch_secret_{k-1}`.

**Post-compromise security** comes from Update / Commit. If an attacker learns a member's leaf key at epoch `k`, the next Commit that re-keys the affected path injects fresh entropy the attacker doesn't have. From epoch `k+1` onward, traffic is again confidential — *provided* the attacker is passive and didn't fork the group.

PCS is the property MLS lifts from Signal's two-party Double Ratchet to N-party groups, with `O(log N)` cost rather than `O(N)`.
